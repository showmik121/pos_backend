# রানবুক: ব্যাকএন্ড ও ডেটাবেস (Supabase)

কিছু ভাঙলে এই পাতা দেখুন। ফ্রন্টএন্ড ও ফোনের ডেটার জন্য `pos_fontend/docs/RUNBOOK.md`।
**এই পাতার restore-ধাপগুলো আমরা এখনো একবারও চালিয়ে দেখিনি।** আসল বিপদের আগে একটি টেস্ট প্রজেক্টে মহড়া দিন (নিচে ৯)।

## ১. কোথায় কী চলছে
- API: Supabase Edge Function `api`, `https://gaxzkbcomeexlnzquvzf.supabase.co/functions/v1/api/`। স্বাস্থ্য-পরীক্ষা: `/health`।
- ডেটাবেস: ওই প্রজেক্টের PostgreSQL। অ্যাপ `pos_app` রোলে ঢোকে (RLS প্রযোজ্য); মাইগ্রেশন `postgres` রোলে।
- ডিপ্লয়: `main`-এ পুশ → CI (টাইপচেক, ইউনিট টেস্ট, Deno বিল্ড) → অটো-ডিপ্লয় → `/health` যাচাই।
- **ডেটাবেসের মাইগ্রেশন CI-তে চলে না।** `npm run db:migrate` (বা `db-migrate.bat`) হাতে চালাতে হয়।
- `[skip ci]` কমিট বার্তায় থাকলে ডিপ্লয় হয় না (শুধু ডক বদলে ব্যবহার করুন)।

## ২. খারাপ কোড লাইভ হলে (API rollback)
1. `git log` দেখে খারাপ কমিট চিহ্নিত করুন।
2. `git revert <কমিট>` করে `main`-এ পুশ করুন। CI পাস করলে পুরনো আচরণ নিয়ে নিজে ডিপ্লয় হবে, শেষে `/health` যাচাই।
3. CI ধীর বা ভাঙা হলে হাতে: `.env` ঠিক রেখে `deploy-supabase.bat` চালান (সবকিছু বিল্ড করে ডিপ্লয় করে)।
4. ডিপ্লয়ের পর `https://.../api/health` খুলুন। `{"status":"ok","db":"ok"}` মানে ফাংশন চালু এবং ডেটাবেসে পৌঁছানো যাচ্ছে। `503` ও `{"status":"degraded","db":"down"}` মানে ফাংশন চালু কিন্তু ডেটাবেস নাগালে নেই (৮ নম্বর দেখুন)। উত্তর ৫ সেকেন্ড পর্যন্ত ক্যাশ হয়। এরপরও একটি লগইন চেষ্টা করুন; `/health` শুধু `SELECT 1` পরীক্ষা করে।

## ৩. মাইগ্রেশন ফেল করলে
- রানার (`scripts/db-migrate.ts`) ফাইলগুলো নামের ক্রমে চালায়, চলা ফাইলের নাম `schema_migrations`-এ লেখে। প্রতিটি ফাইলের ভেতরে `BEGIN … COMMIT` আছে, তাই **একটি ফাইল মাঝপথে ফেল করলে সেই ফাইলের সব বদল ফিরে যায় এবং তার নাম লেখা হয় না।**
- ফেলের পর: ত্রুটি পড়ুন, ফাইল ঠিক করুন, আবার চালান। আগের ফাইলগুলো আর চলবে না।
- **মাইগ্রেশনের `down` (পিছনে ফেরা) নেই।** বিশেষ করে `002_hardening.sql` টাকার কলাম `bigint` পয়সায় বদলেছে ও নাম পাল্টেছে; উল্টানো সহজ নয়। পিছনে ফিরতে হলে ডেটাবেস ব্যাকআপ থেকে restore (৫ ও ৬) বা নতুন মাইগ্রেশন লিখে ঠিক করা (সামনের দিকে ঠিক করাই পছন্দের পথ)।
- **বড় বা ধ্বংসাত্মক মাইগ্রেশনের আগে ৪ নম্বর ব্যাকআপ নিন।**
- লাইভে মাইগ্রেশন চালালে (Supabase MCP বা SQL এডিটর দিয়ে চালালে) পরে `schema_migrations`-এ ফাইলের নাম হাতে ঢোকাতে হবে, নইলে রানার ওটি আবার চালাবে।

## ৪. ব্যাকআপ নেওয়া
**প্রথমে আপনার Supabase প্ল্যান দেখুন (Dashboard → Database → Backups):**
- Pro, Team ও Enterprise প্ল্যানে প্রতিদিন স্বয়ংক্রিয় ব্যাকআপ হয়; Pro-তে শেষ ৭ দিনের পাওয়া যায় ([Supabase: Database Backups](https://supabase.com/docs/guides/database/backups))।
- ফ্রি প্ল্যানে Supabase নিজেই বলছে, নিয়মিত CLI-র `db dump` দিয়ে ডেটা এক্সপোর্ট করে অফ-সাইটে রাখতে। অর্থাৎ ফ্রি প্ল্যানে স্বয়ংক্রিয় ব্যাকআপ নেই; হাতে নেওয়া ব্যাকআপই একমাত্র কপি।
- **PITR** (যেকোনো মুহূর্তে ফেরা) অতিরিক্ত পয়সায় অ্যাড-অন।
- দিনের একটি ব্যাকআপ মানে সর্বোচ্চ প্রায় ২৪ ঘণ্টার বিক্রি হারানোর ঝুঁকি। এতে ঝুঁকি বেশি মনে হলে PITR বা বেশি ঘন ঘন হাতে-ব্যাকআপ লাগবে।

**হাতে ব্যাকআপ (সব প্ল্যানে চলে)** (আপনার কম্পিউটারে `pg_dump` ইনস্টল থাকতে হবে):
```bash
# .env থেকে DATABASE_URL_UNPOOLED (Session pooler, postgres ইউজার) নিন
pg_dump "$DATABASE_URL_UNPOOLED" --format=custom --schema=public --no-owner --no-privileges \
  --file=pos-backup-$(date +%F).dump
```
- ফাইলে দোকান, কর্মচারীর পাসওয়ার্ড-হ্যাশ ও ব্যবসার তথ্য আছে। **গোপন রাখুন:** পাসওয়ার্ড-ম্যানেজারসহ সুরক্ষিত জায়গায়, GitHub বা সাধারণ শেয়ারে নয়।
- কমপক্ষে সপ্তাহে একবার, আর প্রতিটি বড় মাইগ্রেশনের আগে। দুটি আলাদা জায়গায় রাখুন।

## ৫. ডেটাবেস ফেরানো, Pro প্ল্যানে (Dashboard)
1. Dashboard → Database → Backups থেকে তারিখ বাছুন, restore চালান। **restore চলার সময় প্রজেক্ট অনুপলব্ধ থাকে।**
2. শেষে `/health` ও একটি লগইন দেখুন।
3. মনে রাখুন: ফেরালে ওই ব্যাকআপের পরের সব ডেটা হারায়। কার্যক্ষম বিল-ডেটা যেহেতু ফোনে থাকে, সিংক চালু হলে ফোন থেকে আবার পাঠানো যাবে। সিংকের আগে ফোনের লোকাল ডেটাই মূল।

## ৬. ডেটাবেস ফেরানো, হাতে নেওয়া `.dump` থেকে
সবচেয়ে নিরাপদ হলো **নতুন একটি Supabase প্রজেক্টে** ফেরানো, পুরনোটি অক্ষত রেখে:
1. নতুন প্রজেক্ট খুলে `.env`-এ তার `DATABASE_URL_UNPOOLED` ও `POS_APP_PASSWORD` বসান।
2. `npm run db:migrate`: স্কিমা, রোল (`pos_app`), RLS ও অনুমতি তৈরি হবে (শুধু ডেটা ফাঁকা)।
3. ডেটা ঢোকান:
```bash
pg_restore --data-only --schema=public --dbname="$DATABASE_URL_UNPOOLED" pos-backup-তারিখ.dump
```
4. সারি গুনে মেলান (`stores`, `users`, `sales`, `sync_events`)। `schema_migrations`-এ ০০১–০০৪ আছে কি না দেখুন।
5. `.env`/Supabase secrets-এ `DATABASE_URL` নতুন প্রজেক্টের `pos_app.<ref>` ইউজারে বদলান ও ফাংশন আবার ডিপ্লয় করুন (`supabase-project-id.txt`-ও নতুন ref-এ)।
6. ফ্রন্টএন্ডের `NEXT_PUBLIC_API_URL` ও CSP-র `connect-src` নতুন ঠিকানায় বদলাতে হবে (`public/_headers`)।
- ⚠ কলাম/টেবিল-ক্রম বা FK নিয়ে `--data-only` আটকালে ত্রুটি পড়ে সমাধান করুন। এটি মহড়া ছাড়া নিশ্চিত নয় (৯ নম্বর)।

## ৭. গোপন তথ্য বদলানো (rotate)
সব গোপন তথ্য Supabase Edge secrets-এ (`supabase secrets set`) এবং আপনার `.env`-এ; কখনো গিটে নয়।
| কী | বদলালে কী হবে | কীভাবে |
|---|---|---|
| `JWT_SECRET` | **সবাই লগআউট হবে** (পুরনো টোকেন অবৈধ) | ≥৩২ অক্ষরের নতুন মান বানিয়ে secret সেট, ফাংশন আবার ডিপ্লয় |
| `pos_app` পাসওয়ার্ড | ফাংশন ডেটাবেসে ঢুকতে পারবে না যতক্ষণ `DATABASE_URL` না বদলাও | `.env`-এ `POS_APP_PASSWORD` বদলে `npm run db:migrate` (এটি রোলে বসায়), তারপর `DATABASE_URL` secret বদলান |
| `postgres` পাসওয়ার্ড | শুধু মাইগ্রেশন/ব্যাকআপ ব্যাহত | Dashboard-এ রিসেট, `.env` হালনাগাদ |
| Supabase access token (CI) | অটো-ডিপ্লয় থামবে | নতুন টোকেন বানিয়ে GitHub Actions secret `SUPABASE_ACCESS_TOKEN` বদলান |
কোনো গোপন তথ্য কোথাও ফাঁস হয়ে থাকলে প্রথমে বাতিল/বদল, তারপর খোঁজ।

## ৮. ঘটনা ঘটলে প্রথম ১০ মিনিট
1. `/health` ও একটি লগইন চেষ্টা: কোনটি ভাঙছে?
2. Supabase Dashboard → Edge Functions → `api` → লগ। ত্রুটির বার্তা (৫০০-তে `internal`) এখানেই লেখা হয়।
3. সাম্প্রতিক ডিপ্লয় সন্দেহজনক হলে ২ নম্বর (revert)।
4. ডেটাবেস সংযোগ ত্রুটি হলে: `DATABASE_URL` ঠিক আছে কি না (পোর্ট ৬৫৪৩, ইউজার `pos_app.<ref>`), পাসওয়ার্ড বদল হয়েছে কি না।
5. লগইনে ঘন ঘন ৪২৯ এলে রেট লিমিট ঠেকাচ্ছে (`auth_attempts` টেবিল)। ১৫ মিনিট পর খোলে।
6. ডেটা নষ্ট বা হারানোর সন্দেহ: **আর কোনো লেখার আগে ৪ নম্বর ব্যাকআপ নিন**, তারপর ৫/৬।
